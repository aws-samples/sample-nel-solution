# Architecture decisions

This document records the design choices that affect deployment behavior, security, cost, and extension of the sample.

## NEL headers on CloudFront

Use a CloudFront response headers policy for static `NEL` and `Report-To` headers. CloudFront adds configured custom headers to viewer responses, so neither CloudFront Functions nor Lambda@Edge is required.

Default CloudFront quotas relevant to this configuration are:

- 20 custom response headers policies per AWS account.
- 100 distributions associated with one response headers policy.
- 10 custom headers per response headers policy.
- 1,783 characters for one custom header value.
- 10,240 characters for all configured header names and values combined.

The sample needs two custom headers and remains well within these defaults. Edge compute is appropriate only if header values must vary per request. A CloudFront Function associated with a viewer-response event runs before each response is returned, including cached responses; Lambda@Edge adds separate concurrency, request-rate, size, and timeout quotas. Those execution paths add complexity and cost without benefit for static NEL policy values.

Sources: [CloudFront quotas](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-limits.html), [CloudFront response headers policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-response-headers-policies.html), and [CloudFront Functions event purposes](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/function-code-choose-purpose.html).

## NEL metric cardinality

The W3C NEL specification defines 29 predefined network error types and separately defines `ok` as a successful outcome. It also explicitly permits user agents to define custom network error types. The collector also has an anonymous public endpoint, so it cannot assume every request was generated by a conforming browser.

The transform therefore:

- Stores the original `body.type` value in Parquet for forward compatibility and investigation.
- Publishes predefined values directly to the CloudWatch `ErrorType` dimension.
- Aggregates every non-standard value into one `other` dimension.

This preserves the source data while preventing arbitrary dimension values from creating unbounded custom metrics or exceeding the CloudWatch `PutMetricData` limit of 1,000 metrics per request.

Sources: [W3C predefined network error types](https://w3c.github.io/network-error-logging/#predefined-network-error-types) and [CloudWatch PutMetricData API](https://docs.aws.amazon.com/AmazonCloudWatch/latest/APIReference/API_PutMetricData.html).

## Firehose transform and Parquet conversion

Firehose performs the final JSON-to-Parquet conversion using the Glue table schema and Parquet serializer. The Lambda is still required because browser Reporting API deliveries are JSON arrays, while Firehose states that an array of JSON documents is not valid input to its JSON deserializer.

The transform has distinct responsibilities:

1. Decode each Firehose record.
2. Accept one report or a browser report array.
3. Expand arrays into newline-delimited JSON documents.
4. Add receipt time and application version metadata.
5. Publish bounded error-type metrics.
6. Mark malformed records as `ProcessingFailed` for the Firehose error prefix.

Removing Lambda without changing the API integration would cause normal browser batches to fail format conversion. Athena reads the resulting Parquet objects; Athena does not perform this ingestion conversion.

Source: [Firehose record format conversion](https://docs.aws.amazon.com/firehose/latest/dev/record-format-conversion.html).

## Lake Formation

The sample intentionally does not grant `IAMAllowedPrincipals` `ALL`/`Super` access. AWS documents that this compatibility principal effectively causes Data Catalog and S3 access to be controlled solely by IAM. Applying it automatically could bypass an account’s fine-grained Lake Formation governance.

Trade-offs:

| Approach | Benefit | Implication |
|---|---|---|
| IAM path used by this sample | Simple deployment in accounts using default Glue/IAM access | A Lake Formation-enforced account may require explicit organization-specific grants before Firehose or Athena can access the table/data. |
| Broad `IAMAllowedPrincipals` compatibility grant | Restores legacy IAM behavior quickly | Weakens Lake Formation controls for the affected resources and requires elevated grant permissions. |
| Lake Formation hybrid access mode | Incremental migration and principal-level opt-in | Requires account-specific data-location registration and permission administration outside a generic sample. |

The deployment test validates the default IAM path. Teams using Lake Formation should onboard the database, table, S3 location, Firehose role, and analyst principals according to their governance model.

Sources: [Lake Formation initial configuration](https://docs.aws.amazon.com/lake-formation/latest/dg/initial-lf-config.html) and [upgrading Glue permissions to Lake Formation](https://docs.aws.amazon.com/lake-formation/latest/dg/upgrade-glue-lake-formation.html).

## Rate controls

The endpoint uses two independent controls:

- AWS WAF: 1,000 matching requests per 300-second evaluation window for each source IP. AWS WAF checks frequently and enforces near, but not as an exact hard ceiling at, the configured limit.
- API Gateway stage: 100 requests per second with a burst target of 200 across the stage. API Gateway uses a token bucket and may return `429 Too Many Requests` when the target is exceeded.

These numbers are not equivalent. The WAF rule averages about 3.3 requests per second per IP over five minutes. The API Gateway stage target allows up to 100 requests per second in aggregate across many IPs while protecting downstream cost and capacity. The account-level default in `us-east-1` is substantially higher at 10,000 requests per second with a 5,000-request burst bucket, so the stage value is an intentional sample guardrail rather than an AWS quota.

Sources: [AWS WAF rate-based rule settings](https://docs.aws.amazon.com/waf/latest/developerguide/waf-rule-statement-type-rate-based-high-level-settings.html) and [API Gateway throttling](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-request-throttling.html).

## Logging defaults

Lambda structured logging and AWS WAF request logging are separate opt-in controls and both default to off. WAF logging keeps only blocked requests with seven-day retention. Metrics, alarms, and the dashboard remain enabled and can still incur charges.

AWS WAF can inspect up to the first 16 KB of an API Gateway request body by default. The deployed AWS Managed Rules Core Rule Set applies its `SizeRestrictions_BODY` rule first and blocks bodies larger than 8 KB, making 8 KB the effective default request-body ceiling. The positive validation rule also uses `NO_MATCH` when a body exceeds the WAF integration inspection limit, and the WebACL default action is `BLOCK`, so an uninspected body cannot obtain the valid-body label.

Source: [AWS WAF oversized request components](https://docs.aws.amazon.com/waf/latest/developerguide/waf-oversize-request-components.html).
